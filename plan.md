# Dashboard for Stock Insight Engine (pre-M1)

## Context

M0 currently only exposes data through `insight-engine report`, which prints a
plain-text dump of a single `AnalysisReport` to the terminal. Before starting
M1 (guardrail stages 2/3), the user wants a dashboard that lays out **all** the
data the pipeline currently produces — the polished, sourced report *and* the
underlying provenance/audit data (raw fundamentals, prices, sources, guardrail
trail) — in a clearly organized view, to make it easier to eyeball correctness
while M1 adds more guardrail stages.

Decisions from the user:
- **Both** a polished report section and a dev/audit internals section, on one
  page.
- **For now**: a static HTML file generated by a new CLI command — no server.
- **Eventually**: a small frontend backed by a real server (this is exactly
  the M3 "FastAPI read endpoints" milestone already in `CLAUDE.md`, just
  arriving sooner). The design below is deliberately split into a data layer
  and a render layer so that transition is a swap of the render layer only,
  not a rewrite.
- Scope: current snapshot only (single ticker, latest report) — matches M0
  reality, no history browsing yet.

No web/frontend code exists anywhere in the repo today. `fastapi` is already
declared in `requirements.txt`/`pyproject.toml` ("Read API — used at M3") but
unused. No templating engine (e.g. Jinja2) is a dependency — stay stdlib-only
for now to keep M0 modest, per `CLAUDE.md`'s "don't over-engineer" convention.

## Design

New package `src/insight_engine/dashboard/`, split so the future FastAPI
server can reuse the data layer untouched:

### 1. `dashboard/read_model.py` — data assembly (pure, DB-reading, no HTML)

A `build_dashboard_data(conn, ticker) -> DashboardData` function plus small
Pydantic view models, all JSON-serializable (this is the shape a future
`GET /dashboard/{ticker}` endpoint would return verbatim via
`.model_dump(mode="json")`):

```python
class SourceView(BaseModel):
    source_id: str
    source_name: str
    source_url: str
    retrieved_at: str

class FundamentalRow(BaseModel):
    period: str
    metric: str
    value: float
    unit: str
    source_id: str

class PriceRow(BaseModel):
    ts: str
    open: float; high: float; low: float; close: float; volume: int
    source_id: str

class RejectionView(BaseModel):
    stage: str
    reason: str
    offending_text: str
    created_at: str

class ReportView(BaseModel):
    id: str
    status: str
    generated_at: datetime
    data_as_of: datetime
    metrics: dict[str, MetricValue]   # reuse domain.MetricValue
    narrative: str
    claims: list[Claim]               # reuse domain.Claim
    disclaimer: str | None

class DashboardData(BaseModel):
    generated_at: datetime
    instrument: Instrument            # reuse domain.Instrument
    report: ReportView | None         # None only if no approved report ever
    rejections: list[RejectionView]   # from guardrail_rejections for this ticker
    fundamentals: list[FundamentalRow]
    prices: list[PriceRow]
    sources: dict[str, SourceView]    # keyed by source_id, for citation lookups
```

`build_dashboard_data` queries: `instruments` (row for ticker),
`db.latest_approved_report` (+ its `claims` rows) for `report`,
`guardrail_rejections` filtered by ticker for `rejections`, `fundamentals` and
`prices` tables directly for the raw data sections, and `sources` for every
`source_id` referenced anywhere above (metrics, claims, fundamentals, prices)
so the render layer never has to do its own joins. Never fabricates — if no
approved report exists yet, `report` is `None` and the render layer shows an
explicit "no approved report yet" state (never partial/unapproved content,
per spec §5.6).

### 2. `dashboard/render_html.py` — presentation (pure function, no I/O)

`render(data: DashboardData) -> str` returns one self-contained HTML string
(inline `<style>`, a little vanilla JS for collapsing the internals section —
no external assets, so it works fully offline). Escape all text fields with
`html.escape` before interpolating (narrative/claims text is untrusted-ish
LLM/fixture output).

Layout:
- **Header**: ticker, name, exchange, sector — plus a status badge
  (APPROVED/REJECTED/NO REPORT) and the disclaimer banner, always visible per
  hard constraint #7 (disclaimer + `data_as_of` attach to every user-facing
  output).
- **Report section** (polished, top): stat-tile grid for `metrics` (value +
  unit + small `[source]` tag), narrative paragraph, claims list each citing
  its source. Before writing this, load the **dataviz** skill for stat-tile
  layout and color conventions.
- **Internals / audit section** (collapsible, below): sources table
  (provenance ledger), raw fundamentals table, raw price series table, and —
  prominently if non-empty — the guardrail rejection trail for this ticker.
  Also a small static note of which guardrail stages are active (1 + 4 today;
  2/3 scaffolded for M1) so the page doubles as an M1-readiness view.

### 3. CLI wiring — `cli.py`

New subcommand, following the exact pattern of `cmd_report`:

```
python -m insight_engine.cli dashboard [--db PATH] [--ticker AAPL] [--out dashboard.html]
```

`cmd_dashboard`: `_prepare(...)` (same as report/ingest) → run the same
generate → guardrail → `save_report` sequence as `cmd_report` (so the
dashboard reflects a fresh run, including any new rejection) →
`read_model.build_dashboard_data(conn, ticker)` →
`render_html.render(data)` → write to `--out` (default `dashboard.html`) →
print the output path. Reuses `_prepare`, `analyst_agent.generate_report`,
`guardrail.run`, `db.save_report` as-is — no changes to existing report flow.

### 4. Tests — `tests/test_dashboard.py`

Mirror the setup pattern in `tests/test_guardrail.py`: build an in-memory/tmp
DB, run ingest + report to populate an approved report. Then:
- `build_dashboard_data`: assert instrument fields, `report.metrics` contains
  the known pinned values (`pe_ratio=20.0` etc., same as
  `test_known_metric_values_end_to_end`), every `source_id` referenced
  resolves in `data.sources`, `rejections == []` for the happy path.
- A second case seeds a `guardrail_rejections` row directly and asserts it
  shows up in `rejections`.
- `render_html.render`: smoke-test that the returned string contains the
  ticker, the disclaimer text, and no raw Python repr/exception text — assert
  shape/presence, not exact HTML (consistent with this repo's "test shape,
  not wording" convention).

## Verification

1. `PYTHONPATH=src pytest -q` — new `test_dashboard.py` passes alongside the
   existing 20 tests.
2. `PYTHONPATH=src python -m insight_engine.cli dashboard` — generates
   `dashboard.html`; open it in a browser and confirm: disclaimer visible,
   AAPL metrics match the CLI `report` output, claims show source tags,
   internals section lists sources/fundamentals/prices, collapsing works.
3. Manually seed a rejection case (or temporarily break a claim's
   `source_id`) to confirm the rejections panel renders correctly, then
   revert.

## Execution

On approval:
1. Save this plan's content to `plan.md` at the repo root (not just the plan
   mode scratch file).
2. Break the work into discrete tasks via `TaskCreate` and run at least two
   agents in parallel. The `DashboardData`/view models in section 1 above are
   the shared contract that makes the split safe — both agents build against
   that fixed shape instead of blocking on each other:
   - **Agent A — data layer**: `src/insight_engine/dashboard/__init__.py`,
     `src/insight_engine/dashboard/read_model.py` (the Pydantic view models +
     `build_dashboard_data`), and the `build_dashboard_data` half of
     `tests/test_dashboard.py` (the two cases: happy-path approved report,
     and a seeded `guardrail_rejections` row).
   - **Agent B — presentation + wiring**: `src/insight_engine/dashboard/render_html.py`
     (load the **dataviz** skill first), the `cmd_dashboard` subcommand in
     `cli.py`, and the `render()` smoke-test cases in `tests/test_dashboard.py`.
     Builds against the `DashboardData` shape defined in the plan even before
     Agent A's file lands, then integrates once it does.
3. After both land: run `PYTHONPATH=src pytest -q`, then generate and
   manually inspect `dashboard.html` per the Verification section above.
